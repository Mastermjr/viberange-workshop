# 03 — Vector-native forensic transport

VibeRange uses Vector on every controlled evidence-producing system and one
central Vector aggregator on `clickhouse-ir`. Edge systems do not write directly to ClickHouse.

## Data path

```text
Kali auditd + Caldera exports ─┐
k3s audit + Tetragon + CRI logs ├─ Vector protocol/TCP 6000 ─ central Vector ─ ClickHouse
router Zeek JSON ───────────────┘
```

Edge agents remain deliberately narrow: tail native local records, attach
`source_type`, `source_host`, and `range_id`, checkpoint files, buffer on disk,
and send with acknowledgements. Parsing, source timestamp selection, parse-error
handling, and ClickHouse credentials stay on the central host.

## Evidence identity and storage

ClickHouse preserves every accepted record in authoritative `ir.raw_events` and
projects stable source fields into typed, source-native tables. The original
`raw_data`, source timestamp, ingestion timestamp, source host, source type, and
range ID remain available for validation. Malformed expected-JSON records stay
in raw storage and are also copied to `ir.parse_errors` for review.

Run membership is explicit about what is known:

- PCAP manifests and the Zeek records produced from a bounded capture carry the
  experiment's `run_id` directly;
- continuously collected auditd, Kubernetes audit, Tetragon, container, and
  Vector-health records are associated with the measured range and run-time
  boundary unless a stronger source identifier is present;
- Caldera operation and link exports carry their operation/link identifiers and
  are registered with the run manifest; and
- correlation views expose the matching method and time delta rather than
  presenting temporal proximity as causality.

The sealed PCAP remains a hashed router artifact. Vector transports its manifest
and the resulting Zeek JSON, not the PCAP itself. CH-UI and Jupyter query the
same ClickHouse evidence; neither interface creates a second evidence store.

### Workshop-ready clickhouse-ir image

`viberange-clickhouse-ir-debian12-v1-template` preinstalls pinned ClickHouse,
Vector, and CH-UI and carries all schema, config-template, saved-search, and
dashboard definitions. The build initializes an empty ClickHouse `ir` schema.
It does not start with evidence, Vector checkpoints/buffers, CH-UI SQLite, or a
final Vector TOML.

A small first-boot Ansible layer is still required because `range_id`, the range
second octet, listeners, source labels, CH-UI connection identity, and SQL range
filters differ per participant. First boot renders those values, verifies or
migrates the baked schema, seeds CH-UI, and starts services; it should not need
to download the three large applications when their baked checksums match.

## Participant dashboards

CH-UI runs on `clickhouse-ir`, but these dashboards are taught here because they explain whether the Vector/evidence pipeline is working. Participants do not install Vector or edit its TOML.

Open the range-relative CH-UI URL documented in module 02 and begin with:

1. **Live evidence flow** — event arrival by source over time;
2. **Machine evidence coverage** — expected analysis, attacker, victim, and router producers;
3. **Source freshness** — latest source and ingestion timestamps;
4. **Victim forwarding proof** — victim rows, transport age, and source-to-ingest delay;
5. **Kubernetes telemetry proof** — Kubernetes audit, Tetragon, and selected container evidence;
6. **Parse errors/unknown sources** — retained evidence that could not enter an expected typed projection.

Before starting the prepared experiment, confirm expected machines are present and required sources are fresh. During the run, watch evidence volume change without treating a dashboard panel as proof by itself. After completion, module 08 filters the same underlying ClickHouse views by the returned run ID.

Interpret common states:

| Dashboard observation | First question |
|---|---|
| Source is absent | Is it expected for this scenario, disabled, outside the time window, or failing? |
| Source timestamp is stale | Is the producer, checkpoint, buffer, or central sink delayed? |
| Ingestion timestamp lags source time | Is buffering/retry working during an outage? |
| Parse-error rows increase | Was source JSON retained but typed projection rejected? |
| Machine has zero events | Is its Vector service connected to TCP/6000 and producing an expected local record? |

Shared dashboards execute ordinary read-only SQL. ClickHouse remains authoritative, and participants can open the underlying saved query to verify what each panel measures.

## Source contract

| `source_type` | Producer | Expected format |
|---|---|---|
| `linux_auditd` | Kali audit dispatcher | JSON, with original audit line retained |
| `caldera_operation` | Run controller/Caldera export | JSON Lines |
| `kubernetes_audit` | k3s API server | Kubernetes audit JSON |
| `tetragon` | Tetragon JSON export | Tetragon event JSON |
| `container_log` | selected CRI workloads | native CRI log line |
| `zeek` | router Zeek | Zeek JSON with `_path` |
| `vector_internal` | Vector | best-effort health logs |

The central aggregator preserves every accepted event in `ir.raw_events`.
Source-specific SQL views expose stable fields while retaining `raw_data`.
Malformed expected-JSON records are also copied to `ir.parse_errors`; they are
not removed from raw storage.

## Validation

Before participant use, the instructor verifies:

1. Vector and ClickHouse services are active;
2. every edge can reach central Vector on TCP/6000;
3. every required source appears and is fresh in `ir.raw_events`;
4. source-specific tables retain the expected native fields and raw record;
5. parse errors, buffer health, and delivery failures remain visible.

Participants repeat the source-freshness and coverage checks in CH-UI before starting the prepared experiment.
